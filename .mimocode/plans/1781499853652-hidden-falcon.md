# Golem × Docker Agent: 深度对比分析与演进方案

> CEO + 首席架构师视角：从 docker-agent 吸收长处，同时巩固 golem 自身优势

---

## 一、CEO Review: 战略定位对比

| 维度 | Docker Agent | Golem | 判断 |
|---|---|---|---|
| **定位** | "Run AI agents like containers" — 声明式、OCI 分发 | "Go-native AI agent runtime" — 嵌入式、可编程 | 互补定位，无需趋同 |
| **用户** | DevOps/SRE，习惯 YAML + Docker 生态 | Go 开发者，学习 AI agent 架构 | 用户画像不同 |
| **分发** | OCI registry push/pull，Docker Hub catalog | 单静态二进制，Termux 可运行 | golem 的零依赖分发是独特优势 |
| **生态** | Docker Desktop 预装，3.1k star | 教学 + 生产双轨 | golem 应强化教学差异化 |
| **TDD** | 有 eval 框架 + cassette 录制 | 有测试但无 eval 框架 | golem 需补 eval |

### CEO 核心判断

1. **不要抄 YAML 声明式** — golem 的 Go SDK + JSON config 路线适合其目标用户（开发者），YAML 声明式是 docker-agent 的差异化，不是 golem 的
2. **吸收分发理念但用 Go 方式实现** — OCI 分发太重，golem 可以做 `golem share push/pull` 用简单的 tar + registry
3. **多 agent 是必选项** — docker-agent 的 multi-agent 架构是核心竞争力，golem 必须跟进
4. **hooks 是护城河** — docker-agent 的 20+ hook 事件是其可扩展性的关键，golem 只有 4 个 hook

## 二、Eng Review: 架构深度对比

### 2.1 架构分层

| 层 | Docker Agent | Golem | 评价 |
|---|---|---|---|
| `cmd/` | CLI 入口 (cobra) | CLI 入口 (cobra) | 平手 |
| `pkg/` | 核心逻辑 (公开) | `core/` (公开) + `internal/` (私有) | golem 更清晰 |
| `internal/` | TUI、runtime | channels、gateway、wiring | golem 的 layer rules 更严格 |
| `feature/` | 无（全部内置） | mcp、memory、rag、skills、routing | golem 的 feature 模块化更好 |
| `foundation/` | 无 | concurrency、logger、store、term | golem 独有，基础设施层 |

**结论：golem 的分层架构更优**，layer dependency rules 是其核心竞争力。保持不动。

### 2.2 Agent Loop 对比

**Docker Agent:**
```
YAML config → parse → agent loop → Model ↔ Tools ↔ Sub-agents → stream to TUI/API
```

**Golem:**
```
JSON config → parse → ReAct loop → Model ↔ Tools → stream to TUI/CLI/Gateway
                   ↕ (optional)
              Planner → Decompose → Execute steps → Reflect → Revise
```

**关键差异：**
- docker-agent: 单 agent loop + multi-agent delegation（通过 tool）
- golem: 单 agent loop + planner/reflector（内置规划能力）

**建议：golem 保留 planner 优势，同时添加 multi-agent 支持**

### 2.3 Tool 系统对比

**Docker Agent:**
- 20+ built-in tools (filesystem, shell, think, todo, memory, tasks, fetch, script, LSP, API, MCP, A2A, RAG, ...)
- MCP 原生支持 (stdio, remote, Docker container)
- Tool permissions (pattern-based allow/deny/ask)
- Tool confirmation (YOLO mode)

**Golem:**
- 基础 tools (fileops, exec, websearch, database, infra)
- MCP via feature module
- RAG via feature module
- Skills via feature module

**需要吸收的：**
1. **Think tool** — 独立的推理 scratchpad，非常实用
2. **Todo tool** — 任务列表管理
3. **Fetch tool** — HTTP 内容获取
4. **Tool permissions** — 基于 pattern 的权限系统

### 2.4 Hooks 系统对比（最大差距）

**Docker Agent (20+ events):**
```
pre_tool_use, post_tool_use, tool_response_transform,
permission_request, session_start, session_end,
user_prompt_submit, user_steering_messages_submit, user_followup_submit,

subagent_stop, on_user_input, stop,
notification, on_error, on_max_iterations,

```
+ Built-in hooks: add_date, add_environment_info, add_prompt_files, add_git_status, add_git_diff, snapshot, redact_secrets, max_iterations, unload

**Golem (4 events):**
```
BeforeMessage, AfterMessage, BeforeLLM, AfterLLM,
BeforeTool, AfterTool, OnError
```

**需要吸收的 hook events（按优先级）：**
1. `turn_start` / `turn_end` — 每轮 turn 的生命周期
2. `before_llm_call` / `after_llm_call` — LLM 调用前后
3. `pre_tool_use` / `post_tool_use` — 工具执行前后（含 matcher）
4. `session_start` / `session_end` — 会话生命周期
5. `stop` — 模型完成响应
6. `on_error` — 错误处理
7. `permission_request` — 工具审批

## 三、Golem 独有优势（必须保持）

1. **Hexagonal Architecture + Layer Rules** — golem 的分层依赖规则是其核心竞争力，docker-agent 没有这种严格性
2. **CGO_ENABLED=0 + Termux** — 零依赖静态二进制，可在 Android/Termux 运行
3. **Bubble Tea TUI** — 原生 Go TUI，不依赖 Docker
4. **Planner/Reflector/ToolSelector** — 内置任务规划和反思能力
5. **Chinese Learning Guides** — 中文学习指南是独特差异化
6. **Foundation Layer** — 基础设施层设计优雅
7. **Feature Module System** — 可选功能模块通过 CLI flags 启用
8. **Tool Result Dual-Channel** — ForLLM + ForUser 分离输出

### Phase 2: Enhanced Hook System

**Spec:** `openspec/changes/enhanced-hooks/`

**Requirements:**
1. 支持 10+ hook events (turn_start, turn_end, pre_tool_use, post_tool_use, session_start, session_end, before_llm_call, after_llm_call, stop, on_error)
2. Hook 支持 matcher pattern (regex)
3. Hook 可以 block/allow/modify tool calls
4. Built-in hooks (add_date, add_environment_info, add_git_status)
5. Hook 可以注入 additional_context

**Design:**
```go
// core/agent/hooks.go 重构
type HookEvent string

const (
    HookTurnStart       HookEvent = "turn_start"
    HookTurnEnd         HookEvent = "turn_end"
    HookPreToolUse      HookEvent = "pre_tool_use"
    HookPostToolUse     HookEvent = "post_tool_use"
    HookSessionStart    HookEvent = "session_start"
    HookSessionEnd      HookEvent = "session_end"
    HookBeforeLLMCall   HookEvent = "before_llm_call"
    HookAfterLLMCall    HookEvent = "after_llm_call"
    HookStop            HookEvent = "stop"
    HookOnError         HookEvent = "on_error"
    HookBeforeMessage   HookEvent = "before_message"
    HookAfterMessage    HookEvent = "after_message"
)

type HookConfig struct {
    Event   HookEvent
    Matcher string        // regex pattern, "*" = all tools
    Handler HookHandler
    Timeout time.Duration
}

type HookHandler interface {
    Execute(ctx context.Context, input HookInput) (*HookOutput, error)
}

type HookInput struct {
    SessionID string
    CWD       string
    Event     HookEvent
    // Per-event fields...
}

type HookOutput struct {
    Continue         bool              // default true
    StopReason       string
    Decision         string            // "block", "allow", ""
    AdditionalContext string            // inject into conversation
    UpdatedInput     map[string]interface{} // modify tool input
}
```

**Tests:**
- Unit: Hook dispatch, matcher pattern, timeout handling
- Integration: Hook chain execution, blocking behavior
- E2E: Real hook scripts

### 5.2 Test Patterns

```go
// Table-driven tests for hooks
func TestHookDispatch(t *testing.T) {
    tests := []struct {
        name     string
        event    HookEvent
        matcher  string
        toolName string
        want     bool
    }{
        {"match all tools", HookPreToolUse, "*", "shell", true},
        {"match specific tool", HookPreToolUse, "shell", "shell", true},
        {"no match", HookPreToolUse, "shell", "file_read", false},
        {"regex match", HookPreToolUse, "shell|edit", "edit", true},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got := matchTool(tt.matcher, tt.toolName)
            assert.Equal(t, tt.want, got)
        })
    }
}

// Subtests for multi-agent
```
